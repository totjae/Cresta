# 계좌·주문 재동기화 명세

## 1. 목적

서버 재시작, 키움 응답 유실, WebSocket 단절과 외부 주문 발생 시 Cresta 내부 주문·체결·포지션을 키움 계좌의 실제 상태와 안전하게 대조하고 복구하는 절차를 정의한다. 재동기화가 끝나기 전 잘못된 신규 주문이나 중복 주문이 발생하지 않게 하는 것이 목적이다.

## 2. 적용 범위

- 키움 국내주식 모의투자 계좌 1개
- Cresta가 생성한 주문, 체결과 포지션
- 키움 앱 등 외부 채널에서 생성된 주문과 포지션
- 서버 시작·재시작, 장 시작 전 점검과 WebSocket 재연결
- 주문·취소·정정 응답 유실 및 계좌 불일치

재동기화는 상태를 확인하고 복구하는 기능이다. 불일치를 맞추기 위한 보상 매매를 자체적으로 생성하지 않는다.

## 3. 상세 명세

### 3.1 시스템 거래 게이트

재동기화 상태와 주문 허용 여부를 분리해 관리한다.

```text
STARTING
→ RECONCILING
→ READY

RECONCILING
→ DEGRADED
→ HALTED
```

| 상태 | 의미 | 신규매수 | 일반 매도 | Guard 청산 |
| --- | --- | --- | --- | --- |
| `STARTING` | 서비스 기동 중 | 금지 | 금지 | 금지, 상태 확인 후 판단 |
| `RECONCILING` | 키움 계좌 대조 중 | 금지 | 금지 | 기존 청산 주문 추적만 허용 |
| `READY` | 중요 불일치 없음 | 설정에 따름 | 설정에 따름 | 허용 |
| `DEGRADED` | 일부 조회·실시간 기능 저하 | 금지 | 사용자에게 상태 표시 후 제한 | 실행 가능성 확인 후 허용 |
| `HALTED` | 중요한 불일치가 해결되지 않음 | 금지 | 금지 | 자동 재주문 금지, 수동 대응 경보 |

| ID | 요구사항 |
| --- | --- |
| REC-001 | 프로세스 시작 직후 거래 상태를 `STARTING`으로 두고 신규 주문을 금지한다. |
| REC-002 | 재동기화 시작 시 계좌 단위 거래 잠금과 종목별 주문 잠금을 획득한다. |
| REC-003 | 중요 불일치가 없는 것이 확인된 뒤에만 `READY`로 전환한다. |
| REC-004 | 재동기화 기능은 불일치 해소를 위한 매수·매도 주문을 자동 생성하지 않는다. |
| REC-005 | 기존 청산 주문은 중복 제출하지 않고 키움에서 실제 상태를 먼저 확인한다. |

다음 이벤트에서 재동기화를 실행한다.

| ID | 트리거 | 범위 |
| --- | --- | --- |
| REC-010 | 프로세스 시작·재시작 | 계좌 전체 |
| REC-011 | 07:30 장 시작 전 점검 | 계좌 전체 |
| REC-012 | WebSocket 단절 후 재연결 | 단절 구간의 주문·체결 및 전체 포지션 |
| REC-013 | 주문 제출 응답 시간초과 | 해당 주문 그룹·종목 및 포지션 |
| REC-014 | 취소·정정 응답 시간초과 | 원주문, 자식 주문과 해당 종목 |
| REC-015 | 실시간 잔고와 내부 포지션 불일치 | 해당 종목, 반복 시 계좌 전체 |
| REC-016 | 주문 수량 불변조건 위반 | 해당 주문 그룹 및 종목 |
| REC-017 | 사용자 수동 요청 | 선택 범위 또는 계좌 전체 |

권장 기본 주기는 장중 60초다. API 호출 제한과 계좌 규모를 고려해 요청을 분산하며, 실시간 이벤트가 정상이어도 주기 대조를 생략하지 않는다.

| --- | --- |
| REC-020 | 실제 보유·매도 가능 수량은 키움 계좌 조회 결과를 우선한다. |
| REC-021 | 키움 상태로 내부 기록을 덮어쓰지 않고 이전 값과 차이를 감사 이벤트로 남긴다. |
| REC-022 | 손익 귀속을 위해 키움 체결과 Cresta 주문 그룹의 연결을 보존한다. |
| REC-023 | 키움에 없는 AI 판단·승인·정책 데이터는 재동기화로 삭제하거나 변경하지 않는다. |
| REC-024 | 조회 시각, 서버 수신 시각과 원본 응답 해시를 스냅샷에 저장한다. |

### 3.4 계좌 전체 재동기화 절차

계좌 전체 재동기화는 다음 순서를 따른다.

```text
1. 거래 게이트 잠금 및 RECONCILING 전환
2. WebSocket 연결·주문체결/잔고 구독
3. 대조 중 실시간 이벤트를 버퍼에 보관
4. 키움 미체결 주문 조회
5. 대상 기간 체결·주문내역 조회
6. 계좌 보유·매도 가능 수량 조회
7. 하나의 reconciliation snapshot 생성
8. 내부 주문·체결·포지션과 차이 계산
9. 확실한 상태 변경을 DB 트랜잭션으로 반영
10. 버퍼 이벤트를 중복 제거 후 순서대로 재생
11. 키움 상태를 한 번 더 조회해 결과 검증
12. 불일치 분류에 따라 READY/DEGRADED/HALTED 결정
13. 감사 로그, 메트릭과 사용자 알림 기록
```

WebSocket을 먼저 구독하고 스냅샷 조회 중 도착한 이벤트를 버퍼링하여 조회 시작과 완료 사이의 체결 누락을 줄인다. 키움 이벤트에 전역 순번이 없거나 신뢰할 수 없으면 주문번호, 이벤트 유형, 체결 시각, 가격과 수량으로 중복 방지키를 만든다.

| ID | 요구사항 |
| --- | --- |
| REC-030 | 스냅샷 생성 중 도착한 실시간 이벤트를 버리고 진행하지 않는다. |
| REC-031 | 스냅샷 반영과 버퍼 이벤트 재생에는 동일한 중복 제거 규칙을 사용한다. |
| REC-032 | 계좌 전체 결과 반영은 주문·체결·포지션 단위의 원자적 트랜잭션으로 처리한다. |
| REC-033 | 최종 검증 스냅샷이 첫 스냅샷과 계속 달라지면 `READY`로 전환하지 않는다. |
| REC-034 | 실패한 재동기화 실행도 시작·종료 시각, 단계와 실패 원인을 기록한다. |

### 3.5 주문 응답 유실 복구

주문·취소·정정 요청이 시간초과되면 다음 절차를 사용한다.

```text
해당 주문을 UNKNOWN으로 전환
→ 주문 그룹과 종목 잠금
→ 실시간 이벤트 버퍼 확인
→ 키움 미체결 주문 조회
→ 키움 체결·주문내역 조회
→ 실제 잔고 확인
→ 기존 키움 주문 발견 시 내부 주문과 연결
→ 충분한 대조 후에도 불명확하면 RECONCILING 유지
```

동일 주문을 찾을 때는 키움 주문번호가 있으면 그것을 최우선으로 사용한다. 주문번호가 없으면 계좌, 종목, 매수·매도, 주문시각 범위, 주문수량, 주문가격과 원주문번호를 함께 비교한다. 일부 값만 같은 주문을 임의로 연결하지 않는다.

권장 재조회 간격은 `1초 → 2초 → 5초`이며 총 3회다. 이 값은 키움 모의투자 반영 지연을 측정한 뒤 조정한다.

| ID | 요구사항 |
| --- | --- |
| REC-040 | 응답 유실 직후 같은 주문을 재전송하지 않는다. |
| REC-041 | 후보가 하나로 확정되지 않으면 자동 연결하지 않는다. |
| REC-042 | 기존 주문을 찾으면 새로운 주문을 만들지 않고 해당 키움 주문을 추적한다. |
| REC-043 | 3회 대조 후에도 결과가 불명확하면 `HALTED` 또는 종목 격리 상태로 전환한다. |

### 3.6 불일치 유형과 처리

| 불일치 코드 | 상황 | 기본 처리 |
| --- | --- | --- |
| `BROKER_ORDER_MISSING_INTERNAL` | 키움 주문은 있으나 Cresta에 없음 | 외부 주문으로 생성, 종목 신규주문 차단 |
| `INTERNAL_ORDER_MISSING_BROKER` | 내부 미종료 주문이 키움에 없음 | 체결·취소 내역 재조회, 불명확 시 격리 |
| `FILL_MISSING_INTERNAL` | 키움 체결이 내부에 없음 | 중복 확인 후 체결 복원 |
| `FILL_MISSING_BROKER` | 내부 체결이 키움에서 확인되지 않음 | 포지션 갱신 중지, 계좌 전체 재대조 |
| `POSITION_QUANTITY_MISMATCH` | 보유 수량이 다름 | 키움 수량을 운영 기준으로 반영, 중요 경보 |
| `AVAILABLE_QUANTITY_MISMATCH` | 매도 가능 수량이 다름 | 신규 매도 계산 중지, 미체결 주문 재조회 |
| `AVERAGE_PRICE_MISMATCH` | 평균단가가 다름 | 두 값을 보존, 손익 표시 경고 및 원인 조사 |
| `DUPLICATE_FILL` | 같은 체결이 중복 수신됨 | 한 번만 반영하고 중복 이벤트 기록 |
| `UNKNOWN_EXTERNAL_POSITION` | 외부 주문으로 포지션 발생 | 관리되지 않는 포지션으로 격리 |

| ID | 요구사항 |
| --- | --- |
| REC-050 | 불일치를 코드, 심각도, 내부값, 키움값과 해결 상태로 기록한다. |
| REC-051 | 수량 불일치는 손익 표시만 수정하고 끝내지 않고 주문·체결 원인을 추적한다. |
| REC-052 | 명확한 누락 체결은 중복 방지 후 복원할 수 있다. |
| REC-053 | 불명확한 내부 체결을 임의로 삭제하지 않는다. |
| REC-054 | 중요한 수량·주문 불일치가 있는 종목은 신규 주문을 차단한다. |

### 3.7 외부 주문과 포지션

키움 앱 등 Cresta 외부에서 생성된 주문은 자동으로 특정 전략에 편입하지 않는다.

```text
외부 주문 발견
→ EXTERNAL_UNMANAGED 표시
→ 해당 종목 Cresta 신규주문 차단
→ 체결·미체결 지속 추적
→ 사용자에게 해결 선택 요청
```

사용자 해결 선택:

- `ADOPT_AS_MANUAL_POSITION`: 수동 관리 포지션으로 편입하고 손절·익일 보유 정책을 새로 설정
- `CANCEL_EXTERNAL_ORDER`: 외부 미체결 주문 취소를 별도 승인 후 요청
- `LIQUIDATE_EXTERNAL_POSITION`: 별도 매도 승인과 Guard 검사를 거쳐 청산
- `KEEP_HALTED`: 상태를 바꾸지 않고 해당 종목 자동 거래를 계속 차단

`ADOPT_AS_MANUAL_POSITION`에는 최소한 확인된 보유수량·키움 평균단가, 고정손절 사용 여부와 값, 익일 보유 정책, 부분·전량매도 실행 모드가 필요하다. 키움 평균단가와 내부 계산값이 다르면 포지션·주문 가능 수량은 키움 값을 사용하고, 손익 화면에는 `BROKER_BASIS` 표시와 차이를 함께 노출한다. 원인이 해결되기 전 내부 과거 체결을 삭제하거나 평균단가를 조용히 덮어쓰지 않는다.

| ID | 요구사항 |
| --- | --- |
| REC-060 | 외부 주문·포지션에 AI 전략과 손절 정책을 자동 부여하지 않는다. |
| REC-061 | 외부 포지션을 숨기거나 내부 수량에서 제외하지 않는다. |
| REC-062 | 외부 주문 취소·청산은 재동기화 절차가 아니라 별도 사용자 의도와 주문으로 감사한다. |
| REC-063 | 외부 포지션 해결 전 해당 종목의 자동·승인 신규매수를 모두 차단한다. |
| REC-064 | 외부 포지션 편입은 필수 손절·익일 보유·매도 실행 정책과 사용자 승인을 요구한다. |
| REC-065 | 평균단가 불일치 중 거래 기준은 키움 보유정보를 사용하고 화면에 기준과 차이를 표시한다. |

### 3.8 완료 판정

다음 조건을 모두 만족해야 `READY`로 전환한다.

1. 모든 키움 미체결 주문이 내부 주문 또는 외부 주문 레코드와 연결됨
2. `UNKNOWN`, `SUBMITTING`, `CANCEL_PENDING`, `REPLACE_PENDING` 주문이 근거 없이 방치되지 않음
3. 키움 보유 수량과 내부 운영 수량이 종목별로 일치함
4. 체결 중복과 수량 불변조건 위반이 없음
5. WebSocket 주문체결·잔고 구독이 정상 또는 허용된 제한운영 상태임
6. 중요도 `CRITICAL` 불일치가 미해결 상태가 아님

외부 포지션이 있더라도 계좌 전체를 반드시 중단할 필요는 없다. 해당 종목을 `EXTERNAL_UNMANAGED`로 격리하고 다른 종목이 안전하면 제한적으로 `READY`가 될 수 있다. 계좌 한도 계산에는 외부 포지션 평가금액을 포함한다.

### 3.9 저장 및 관측성

재동기화 실행마다 다음 정보를 저장한다.

```yaml
reconciliation_run:
  id:
  trigger:
  scope:
  status:
  started_at:
  completed_at:
  snapshot_at:
  attempt_count:
  mismatch_count:
  critical_mismatch_count:
  broker_request_ids:
  correlation_id:
```

메트릭:

- 재동기화 성공·실패 횟수와 소요시간
- 트리거별 실행 횟수
- 불일치 코드별 발생 횟수
- `UNKNOWN` 주문 해결시간
- 외부 주문·포지션 수
- `RECONCILING`, `DEGRADED`, `HALTED` 지속시간

### 3.10 첫 키움 스냅샷 대조 단계

첫 구현은 주문을 생성하거나 broker 값을 내부 포지션에 자동 덮어쓰지 않는 읽기 전용 대조 단계다.

```text
계좌 10자리 일치 확인
→ 거래 게이트 RECONCILING
→ ka10075 미체결 전체 페이지
→ ka10076 당일 체결 전체 페이지
→ kt00018 평가잔고 전체 페이지
→ 내부 KIWOOM_MOCK_PRIMARY 미종료 주문·포지션과 비교
→ run/mismatch 원자 저장
→ 불일치 없음: RECONCILING(PERMANENT_WORKER_REQUIRED)
→ 중요 불일치: HALTED(RECONCILIATION_MISMATCH)
→ 조회 실패: DEGRADED(RECONCILIATION_FAILED)
```

| ID | 요구사항 |
| --- | --- |
| REC-070 | 계좌 alias는 `KIWOOM_MOCK_PRIMARY`, 환경은 `MOCK`, trigger는 `MANUAL_BOOTSTRAP`으로 고정한다. |
| REC-071 | 대조 시작 전에 gate를 `RECONCILING`으로 저장하고 어떤 종료 경로에서도 `READY`로 전환하지 않는다. |
| REC-072 | broker 미체결 주문과 내부 활성 주문은 broker 주문번호로 비교한다. 어느 한쪽에만 있거나 종목·방향·주문/잔여수량이 다르면 `CRITICAL` mismatch다. |
| REC-073 | broker 보유수량과 내부 OPEN 포지션은 종목별로 비교한다. 외부 포지션, 내부 누락, 수량·평균단가 차이는 mismatch로 기록하며 자동 편입·수정하지 않는다. |
| REC-074 | 당일 체결은 주문번호별 체결수량 합계와 내부 체결수량의 차이를 탐지하는 데만 사용하고 개별 Fill을 생성하지 않는다. |
| REC-075 | 실행 결과는 snapshot 건수·mismatch 코드/심각도·시각·요청 API ID만 저장한다. 전체 계좌번호·token·원본 broker payload는 저장하지 않는다. |
| REC-076 | mismatch가 없으면 run은 `SUCCEEDED`, gate는 `RECONCILING/PERMANENT_WORKER_REQUIRED`다. 하나 이상의 `CRITICAL` mismatch가 있으면 run은 `MISMATCH`, gate는 `HALTED/RECONCILIATION_MISMATCH`다. |
| REC-077 | 조회·정규화·DB 반영이 실패하면 run은 `FAILED`, gate는 `DEGRADED/RECONCILIATION_FAILED`다. CLI는 안정된 오류 코드와 비밀이 없는 요약만 출력한다. |

### 3.11 상시 worker 재동기화

| ID | 요구사항 |
| --- | --- |
| REC-078 | worker 재동기화 trigger는 `WORKER_STARTUP`, `WEBSOCKET_RECONNECTED`, `BROKER_EVENT`, `PERIODIC` 중 하나로 기록한다. 수동 CLI는 기존 `MANUAL_BOOTSTRAP`을 유지한다. |
| REC-079 | worker가 실행한 clean 대조도 reconciliation 함수 단독으로 READY를 만들지 않는다. 호출자가 현재 lease·LOGIN·구독을 재검증한 뒤 별도 transaction에서 READY를 확정한다. |
| REC-080 | `00`·`04` 실시간 이벤트는 직접 주문·체결·포지션 변경 근거가 아니라 REST 대조 trigger로만 사용한다. 1초 안의 연속 이벤트는 하나로 합칠 수 있다. |
| REC-081 | 주기·이벤트 대조 중 mismatch는 즉시 `HALTED`, 조회 실패는 `DEGRADED`로 전환하며 이전 READY 상태를 보존하지 않는다. |

## 4. 오류·예외 또는 경계 조건

- 키움 조회 API 일부만 성공하면 성공한 스냅샷으로 전체 계좌를 확정하지 않는다.
- 조회 중 체결이 계속 발생하면 버퍼 이벤트 반영 후 최종 검증을 반복하되 무한 반복하지 않는다.
- 반복 한도를 넘기면 `DEGRADED` 또는 `HALTED`로 전환하고 사용자에게 알린다.
- 체결 내역 조회 기간 경계 때문에 전일 주문이 누락되지 않도록 미종료 내부 주문은 거래일이 바뀌어도 조회 대상에 포함한다.
- 외부 주문이 Cresta 주문과 우연히 조건이 같더라도 키움 주문번호나 충분한 식별 근거 없이 자동 연결하지 않는다.
- 재동기화 중 데이터베이스 저장 실패가 발생하면 일부만 반영된 것으로 간주하고 전체 대조를 다시 수행한다.
- 키움 API 호출 제한을 지키며 rate limit 오류 시 재시도 시간을 늘리고 신규매수를 차단한다.

## 5. 검증·인수 조건

- 서버 재시작 후 계좌 전체 대조가 끝나기 전 신규 주문이 생성되지 않는다.
- 스냅샷 조회 중 들어온 체결 이벤트가 유실되거나 중복 반영되지 않는다.
- 주문 응답이 유실됐지만 키움에 접수된 주문을 찾아 기존 주문과 연결한다.
- WebSocket 단절 중 발생한 부분체결을 REST 조회로 복원한다.
- 내부에 없는 외부 주문과 포지션을 감지하고 해당 종목을 격리한다.
- 키움 보유 수량과 내부 수량이 다르면 키움 수량을 운영 기준으로 사용하고 감사 기록을 남긴다.
- 불명확한 주문을 임의로 실패 처리하거나 재전송하지 않는다.
- 재동기화 실패 시 시스템이 `READY`로 잘못 전환되지 않는다.
- 모든 불일치가 코드와 해결 상태를 포함해 조회 가능하다.

## 6. 미결정·보류 항목
